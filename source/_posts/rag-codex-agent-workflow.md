我在教 Codex 的時候，最常遇到的不是「學生不會下 prompt」，而是他們還不知道自己要讓 AI 改什麼。很多人一開始會很自然地把 Codex 想成一個比較會寫程式的聊天機器人，但真正進到專案裡，事情就沒有那麼簡單。你要先知道這個 repo 在做什麼、哪些檔案是入口、哪些地方不能亂動、改完之後怎麼檢查，AI 才有可能幫上忙。

所以我通常不會一開始就叫學生丟一句很大的指令。尤其是國中生，我會先讓他們看到一個很小的修改：例如改一段文字、調整一個按鈕、修正一個畫面，再觀察 GitHub 裡的檔案如何變動。當他們知道「一次修改」其實會落在具體檔案、具體行數、具體 commit 裡，AI 協作才會從魔法變成可以理解的工程流程。

教大學生、碩士生、博士生或成人學習者時，我會把焦點拉到另一層。他們常常已經有自己的研究、產品或工作流程，所以更重要的是把專案規則寫清楚。這時候我會很重視文件，像是 README、設計筆記、AGENTS.md、任務說明、測試方式。這些文件不是裝飾，而是讓 AI 不要每次都重新猜測專案脈絡的方式。

RAG 對我來說也是同一件事的延伸。不是因為 RAG 這個詞很新，所以就要放進專案裡；而是當一個學習平台有很多教材、規則、解題脈絡或使用者紀錄時，AI 必須能回到指定資料裡找根據。否則它講得再順，也可能只是把看似合理的內容補起來。教學系統不能只追求流暢，還要能回到資料、回到題目、回到學生真正卡住的地方。

我自己比較喜歡把 Codex 教成一種工作習慣，而不是一堂工具課。第一步是把模糊需求寫清楚，第二步是讓 AI 做小範圍修改，第三步是看 diff，第四步才是決定要不要接受。這個順序看起來慢，但對初學者很重要，因為他們會慢慢理解：軟體工程不是把答案生出來，而是讓每一次修改都能被理解、被檢查、被接續。

我在分享會裡也常談這件事。AI 讓很多人第一次有能力碰到大型專案，但它同時也會放大原本沒有說清楚的地方。如果需求模糊，AI 會用自己的方式補；如果文件散亂，AI 會抓錯重點；如果沒有測試，改完看起來能跑，卻不一定真的可靠。這些問題不是反對 AI，而是提醒我們要把工程的地基打好。

因此，我的 Codex 教學核心其實很樸素：讓不同背景的人能一步一步理解，自己正在要求 AI 做什麼，以及做完之後要如何判斷它有沒有做對。只要這件事成立，無論學生是在改一個小網頁、做數學教學平台，或是把自己的研究流程變成工具，都會比較有機會走得下去。
